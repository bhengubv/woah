# Woah! level editor — design (v1)

Agreed 2026-09-11. Builds on the July decisions (assist, never autonomous generation; the
designer is the validator; tier, don't gate) and the ecosystem principle that an editor
teaches by **remixing something somebody handed you**, not by a create-new wizard.

## The shape of it

- **Authored, socketed tiles on a grid.** A small catalogue we define in code (rooms,
  halls, corners, junctions, stairs, lift, arena, start, exit) that join at door sockets.
  Not Freedoom sectors glued together — their geometry is freeform and does not compose.
  Freedoom (BSD) supplies the **dressing**: texture pairings, light levels, room heights and
  monster mixes, harvested by `tools/prefab/extract.py` into `palettes.json`.
- **Valid by construction.** Tiles never overlap and every tile is built from axis-aligned
  rectangles, so the compiler builds the BSP itself with axis-aligned splits (a rectangle cut
  by a straight line is two rectangles; leaves are the subsectors). No node-builder library,
  nothing precomputed per tile — and every level the editor lets you play is a level the
  engine can load. (M1 finding, 2026-09-11: this replaced the earlier "precomputed BSP piece
  per tile" idea; it is simpler and covers tiles of any shape made of rectangles.)
- **Geometry tiles + a separate population layer.** Tiles carry typed spawn slots; a
  population preset fills them. Same layout, different difficulty; the marines dial is
  untouched because bots are players, not monsters.
- **Remix-first.** The editor always opens *on* a level — a starter or a card someone sent
  you. Layout → dressing → population → lumps, revealed progressively. Nothing opens blank.
- **The level is a card**, a few hundred bytes of JSON. Sharing rides AetherNet on any
  transport, LoRa included; the WAD is compiled on the phone from the card. The trading is
  the teaching.
- **Same APK.** An editor Activity (touch, top-down grid); Play launches the game with
  `-file <compiled>.wad`. Everything in the DOOM APK is GPLv2, which is fine for our code.
- **AI assist = ButlerAPI, out of process**, editing the card through a fixed op
  vocabulary; the editor validates every op the same way it validates a finger.

## The card

```json
{
  "woah": 1,
  "name": "First light",
  "author": "aether:tag-or-name",
  "based_on": null,
  "grid": 64,
  "tiles": [
    {"t": "start",  "x": 0, "y": 0, "r": 0, "dress": "tech"},
    {"t": "hall_ew","x": 4, "y": 1, "r": 0, "dress": "tech"},
    {"t": "room_m", "x": 8, "y": 0, "r": 0, "dress": "base"},
    {"t": "exit",   "x": 14,"y": 1, "r": 0, "dress": "base"}
  ],
  "doors": [[0, 1], [1, 2], [2, 3]],
  "pop": {"preset": "normal", "slots": {"2/1": "imp"}}
}
```

- `grid` is map units per cell; tile footprints are whole cells (4×4 … 8×8).
- `r` is rotation in quarter turns. `doors` pairs tile indices whose sockets touch.
- `pop.slots` overrides a slot (`tile/slot` → role or monster) on top of the preset.

## The tile catalogue (`assets/tiles.json`, generated by `tools/tiles/`)

Per tile: `id`, footprint `(w, h)` in cells, `sockets` `[{edge: N|E|S|W, offset, width}]`,
local geometry (vertices, linedefs, sidedefs, sectors) with texture **roles**
(`wall`, `floor`, `ceil`, `door`, `trim`, `step`) that a dressing resolves, precomputed local
`subsectors/segs/nodes`, thing `slots` `[{x, y, role}]` with roles
`player | monster_s | monster_m | monster_l | ammo | health | armor | key | secret`, and
provenance for anything derived from Freedoom.

Initial set (~24): `start`, `exit`, `room_s`, `room_m`, `room_l`, `hall_ns`, `hall_ew`,
`corner` (×4 by rotation), `t_junction`, `cross`, `stairs` (floor delta), `lift`, `arena`,
`pillar_room`, `courtyard`, `nook` (secret).

## Compilation (on the phone; deterministic; Java mirrors a Python reference)

1. Place tiles; reject overlaps; every door must pair two touching, matching sockets.
2. Emit `VERTEXES / LINEDEFS / SIDEDEFS / SECTORS / THINGS` by offsetting each tile's local
   data; a door socket becomes the two-sided line (or door sector) between the two tiles.
3. Nodes by axis-aligned splits over all sector rectangles (kd-tree; a straddling rectangle is
   cut into two). Each leaf rectangle is a subsector whose segs are the pieces of linedefs
   along its edges. `tools/tiles/compile.py` is the reference; `lint.py` re-reads the output
   and checks every index, the tree walk and the blockmap before a WAD reaches a phone.
4. `BLOCKMAP`: rasterise linedefs into 128-unit blocks. `REJECT`: all zero (valid, no culling).
5. Write a PWAD with `MAP01`; play with `-file <card>.wad -warp 1`.

The editor is the validator: sockets, one player start per slot, and reachability
start→exit using the bots' BSP navmesh query (`p_botnav`), which already answers "is the
exit reachable".

## Dressing

A dressing is `{floor, ceil, wall, trim, light}`. v1 ships three presets from the top
pairings in `palettes.json`: `tech`, `base`, `hell`. Progressive reveal: pick a look, then
see the textures it resolves to, then the lumps.

## Population

Presets `easy / normal / hard` fill slots by role using the palette's monster mixes by room
size; per-slot overrides live in the card. The dial (marines with you / against you) is a
separate layer and needs nothing from the card.

## Editor UI

Top-down grid canvas (pan, pinch). Tap a tile in the palette, tap the grid to place; tap a
placed tile to rotate / dress / remove; doors are suggested wherever sockets touch; **Play**;
**Share** (the card, via the system share sheet, txtMe!, the Arcade); **Remix** opens a
received card. The screen-size and touch-precision limit is the real constraint on low-spec
phones, not the SoC — tiles keep every touch coarse.

## AI assist

Ops on the card: `add_tile`, `remove_tile`, `move_tile`, `connect`, `dress`, `populate`.
B! proposes ops from a sentence ("add a courtyard after the second hall, make it harder");
the editor applies them through the validator and shows the result; the human keeps
authorship and can reject. Rejections stay private, in the room.

## Milestones

- **M1** `tools/tiles/`: catalogue + Python reference compiler + validator → a playable
  `MAP01` compiled from a card, running on the P30.
- **M2** Java compiler + `EditorActivity` (place, rotate, door, dress, play).
- **M3** Share / Remix + population presets.
- **M4** AI ops via ButlerAPI.
